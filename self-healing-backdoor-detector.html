What is a self-healing backdoor?

A self-healing backdoor is malware that reinstalls itself after deletion using redundant persistence mechanisms — scheduled tasks, rogue admin accounts, and hidden plugins that watch and restore each other.

You deleted the suspicious file. You changed the passwords. And then — it came back. That is not bad luck: it is the signature of a self-healing WordPress backdoor, a new strain that repairs itself every time you try to remove it. This free checklist helps you work out whether that is what is happening on your site, and shows the exact removal order that actually ends it. Why does WordPress malware keep coming back after I delete it?

Because the file you deleted is the symptom, not the reinfection path. Self-healing malware persists through multiple footholds — rogue admin accounts in the database, wp-cron jobs that re-download the payload, and a mu-plugin that WordPress loads first. Until every foothold is removed in the right order (database first, then mu-plugins, then cron, users, and salts), one survivor rebuilds everything.

The threat, in plain English

  • Delivered as a must-use plugin. The backdoor installs itself into wp-content/mu-plugins/ — the one folder WordPress loads automatically, before everything else, with no activation step and nothing to toggle off in wp-admin.
  • Self-healing by design. It carries mechanisms that rebuild the backdoor after removal attempts, so wiping the obvious file is only round one of a fight it is built to win.
  • EtherHiding for its command server. The attacker's control location is hidden behind an Ethereum smart contract instead of a domain or IP, making the infrastructure takedown-resistant — there is no single server to seize.
  • Full site takeover kit. It establishes hidden rogue admin accounts, harvests admin passwords, allows remote modification of the site, exfiltrates data, and can spread laterally to other sites on the same hosting.

Why normal deletion fails — and the order that works

A self-healing backdoor is never one file. It is a set of footholds that rebuild each other: the mu-plugin, rogue database entries, scheduled tasks, and compromised accounts. Delete one and the others restore it. That is why you must work in an order where no surviving foothold can re-infect what you already cleaned:

  1. Contain first. Put the site in maintenance mode (or take it offline) and back up what's left — you'll need a copy for reference, but restore only from a backup that predates the infection.
  2. Database first. Rogue admin accounts and malicious cron entries live in the database, not in files. Remove unknown users and suspicious scheduled tasks before touching a single file — otherwise they re-plant the payload the moment you look away.
  3. Then the mu-plugins folder. Clear wp-content/mu-plugins/ of anything you didn't place there yourself. Do the database first (step 2), or a surviving cron job re-drops the file.
  4. Then scheduled tasks at the server level. Check wp-cron and real server cron jobs your host may run — either can be the reinfection timer.
  5. Then users and passwords. Force a password reset for every legitimate account, remove the rogues' accounts entirely, and review who has what role.
  6. Finally, rotate the salts. Regenerate the security keys and salts in wp-config.php to invalidate every existing session and cookie — this locks out anyone still holding a stolen session.
  7. Reinstall from clean sources. Reinstall WordPress core and every theme and plugin from official sources. Assume every file the attacker could touch is untrustworthy until replaced.
If anything in step 2–6 makes you nervous: get professional help before you keep clicking. A half-finished cleanup is how sites get re-infected twice. The wrong order — files before database — is the single most common reason the backdoor "comes back."

FAQ

What is a self-healing WordPress backdoor?

It is a WordPress backdoor that repairs itself after you try to remove it. Per Wordfence research reported by The Hacker News ThreatsDay bulletin in October 2026, this variant is delivered as a must-use plugin (mu-plugin) with self-healing mechanisms, so deleting the malicious file alone does not end the infection — it restores itself from the other footholds it created.

Can a WordPress backdoor survive a full file cleanup?

Yes. Community members on r/WordPress documented a self-healing attack that survived a full file-level cleanup and returned within 24 hours, because persistence lived in the database and in wp-config.php, not just on disk: base64 payloads in wp_options transients, malicious mu-plugins, and a restore routine that rewrites plugin files from the database on every page load. (Per WPTips, Oct 2026: https://wptips.com/guides/self-healing-wordpress-malware-survives-file-cleanup/)

Why does the WordPress malware keep coming back after I delete it?

Because you are removing the symptom, not the reinfection path. Self-healing backdoors persist through multiple footholds: rogue admin accounts in the database, scheduled tasks (wp-cron) that re-download the payload, and the mu-plugin itself, which WordPress loads before anything else. Until every foothold is removed in the right order, one survivor rebuilds the rest.

How do I check my mu-plugins folder for malware?

Connect over SFTP (or your host's file manager) and open wp-content/mu-plugins/. Any legitimate site rarely needs files there, so anything you did not put there yourself deserves suspicion. Compare the file dates against your last legitimate change, and if you are unsure what a file does, treat the whole site as compromised and follow the full removal order rather than deleting one file.

What is the correct order to remove a persistent WordPress backdoor?

Take the site offline or into maintenance mode first, then work in this order: the database (rogue admin accounts and malicious cron entries live here), the mu-plugins folder, scheduled tasks, all user accounts and passwords, and finally rotate the security salts in wp-config.php. Then reinstall WordPress core and every theme and plugin from clean sources. Doing it in any other order lets a surviving foothold re-infect the parts you already cleaned.
