That missing middle is where the damage lives. A malicious npm package rarely needs an exotic exploit: it needs an install. The moment a developer or a CI runner executes npm install, the package's own lifecycle scripts run with that user's permissions, that machine's files and that environment's tokens. An advisory that says only “malicious package, remove it” leaves the three questions that matter unanswered — what ran, what it could reach, and what you must rotate. What is a yanked package?

A yanked package is a package version pulled from a registry after publication, usually because it was flagged as malicious or compromised. Pulling it stops new downloads from the registry, but it does not remove copies already cached, vendored or pinned in your lockfile — those still install and still run.

Registries yank, flag or unpublish for different reasons — malware, a hijacked maintainer account, a protest, or a broken release — and the response differs for each. When the reason is malware, the safe assumption is that the package's install-time code executed everywhere it was installed, on laptops and in CI alike. That assumption, not the advisory label, should drive your response.

    Pulled package? Do this now

    If a package in your tree was yanked or flagged, work this list in order. Speed matters more than completeness in the first hour; you can deepen the investigation once the exposure window is closed.

    1. Stop the installs. Pause CI pipelines and deploys that run npm install on the affected lockfile, and tell the team not to install or update until you say so. Every fresh install is a fresh execution of the flagged code.
    2. Find where it lives. Search every lockfile and manifest for the package name and the flagged versions: grep -rn "item-validator" package-lock.json yarn.lock pnpm-lock.yaml — and note when it entered, from your version-control history.
    3. List the blast radius. Write down every machine and CI runner that installed it in that window. Those systems — not the package — are now the incident.
    4. Remove and pin. Delete the dependency and its lockfile entries, pin a known-good replacement or version, and regenerate the lockfile. Do not just bump and hope: confirm the flagged name is gone from the resolved tree.
    5. Rotate in exposure order. First the npm token and any token present in the install environment, then cloud keys, then GitHub tokens and SSH keys if home-directory files were reachable. Revoke the old values — a new token next to a still-valid stolen one changes nothing.
    6. Hunt for leftovers. Install scripts can persist: review shell startup files, CI configuration, scheduled tasks and recently modified files on affected machines for additions you do not recognize. Deleting node_modules alone does not do this — see the FAQ below.
    7. Review the logs. Check npm, GitHub, cloud and CI audit logs for the exposure window: new tokens created, unfamiliar logins, unexpected publishes or downloads.
    8. Reinstall clean, then prevent the repeat. Reinstall from the cleaned lockfile in a fresh environment. Going forward, consider --ignore-scripts for untrusted installs, review new dependencies' install hooks before adopting them, and audit the tree when advisories land — the analyzer above takes under a minute.

    Frequently asked questions

    What should I do when a dependency is yanked or flagged as malware?

    Stop installing it, pin or remove the flagged version, and check when it entered your lockfile and which machines installed it. Treat any machine that ran its install scripts as exposed: rotate the credentials listed below, review CI logs for that window, and reinstall from a clean lockfile only after the replacement is verified.

    Which credentials should I rotate first after installing a pulled package?

    Rotate in exposure order: first the npm token and any token the install environment held, then cloud keys such as AWS credentials, then GitHub tokens and SSH keys if the script could read your home directory. Revoke the old values rather than just creating new ones, and check each account for activity you do not recognize.

    How do npm install hooks work?

    npm runs lifecycle scripts declared in package.json automatically during install: preinstall runs before the package is installed, install during it, and postinstall after it. Those scripts execute with your user permissions and your environment, so a malicious hook does not need a vulnerability — installing the package is the execution.

    Is deleting node_modules enough after a malicious install?

    No. Deleting node_modules removes the package files, but an install script has already run with your permissions: it may have copied credentials out, changed configuration, or left files elsewhere. Remove the package and its lockfile entry, rotate exposed credentials, review shell and CI configuration for additions, and reinstall cleanly — treat deletion as step one, not the fix.
