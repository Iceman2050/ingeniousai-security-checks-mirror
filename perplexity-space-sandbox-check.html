Perplexity SPACE: AI Agents 2026 Sandbox, Adversarially Tested

On October 15, 2026, Perplexity open-sourced the infrastructure it trusts with every one of its own ai agents 2026 sessions: SPACE (Sandboxed Platform for Agentic Code Execution) — Rust, Apache 2.0, Firecracker microVMs, ~60ms spin-up. Then it did something unusual: it published the results of trying to break it. 108 adversarial escape attempts, zero VM-to-host escapes — and 11 network-policy bypasses in 54 partial-access runs. This page covers what SPACE proves about agent containment, and what it honestly doesn't.

What is Perplexity SPACE for ai agents 2026?

SPACE is the sandbox Perplexity built for its own agents and then gave away. Every Perplexity Computer agent session has run inside it since July 2026. The design principle is stated plainly: the agent is treated as untrusted. Network access and credentials are managed outside the virtual machine, so a compromised agent finds no keys to steal and no open routes to exploit — at least in theory.

What is the "Escaping SPACE" security report?

On September 23, 2026 — three weeks before open-sourcing — Perplexity published "Escaping SPACE: Part I," its own adversarial evaluation. The headline number: zero VM-to-host escapes in 108 attempts. The uncomfortable number, in the same report: 11 network-policy bypasses in 54 partial-access runs. The VM held; the rules about what the agent was allowed to reach did not. Perplexity says it hardened the gateway defenses afterward and follow-up tests came back clean.

Honest scope: this is Perplexity's own reported testing — not an independent audit, not a guarantee. Treat the numbers as a data point from the vendor with every incentive to look good. The pattern it reveals (isolation strong, policy weak) matches what independent sandbox tests keep finding.

What is the difference between a VM escape and a network-policy bypass?

A VM escape breaks the isolation boundary itself — the agent gets out of the virtual machine and onto the host. That is the catastrophic failure, and SPACE reportedly stopped all 108 attempts. A network-policy bypass is subtler: the sandbox holds, but the agent reaches network resources its policy should have blocked — an internal API, a metadata endpoint, a service it was never meant to see. The agent is still "inside" — and still doing damage. Isolation without correct policy is an empty box with the door propped open.

What SPACE proves — and what it doesn't

Proven: Firecracker microVMs are a genuinely strong isolation layer. Two independent data points now agree — SPACE's 108-attempt shutout, and the Trail of Bits test where GPT-5.6-Cyber broke out of QEMU/KVM three times but never completed an escape from Firecracker (it hard-locked the box instead).

Not proven: that the policy layer is correct. Eleven bypasses in 54 runs is a 20% failure rate on the rules that decide what the agent may touch. A sandbox answers "can the agent get out?" — it does not answer "should the agent be allowed to do this?" That second question is identity, least privilege, and monitoring: layers no VM provides.

Who is adopting SPACE?

  • Akamai — launched SPACE on its cloud at release.
  • Crusoe — using it inside its Managed AI Services.
  • CoreWeave — using it for evaluation guidance.

Adoption by infrastructure providers matters: it means the sandbox is being exercised against real workloads, not just the vendor's own test suite. It does not mean the network-policy layer has been independently verified.

What good agent containment looks like

  • Isolation + policy, both tested. SPACE's own report is the lesson: test the boundary and the rules. Adversarial-test your network policy the way Perplexity tested its VMs.
  • Credentials never inside. Inject per-task, revoke after. An agent that can't see a key can't leak one.
  • Identity for every action. Know whether the human, the agent, or generated code made the call — so bypasses are attributable, not anonymous.
  • Monitor the containment zone. Log tool calls, watch for policy-shaped probing, and treat the sandbox as monitored infrastructure, not a guarantee.

Does open-sourcing a sandbox make agents safe?

No. Open-sourcing a sandbox lets everyone inspect the isolation layer — which is genuinely valuable for finding bugs — but a sandbox is one layer, not a verdict. SPACE's own testing showed the VM boundary holding while network policy failed, which is exactly why defense in depth (identity, least privilege, monitoring, logging, application-level controls) remains mandatory even with a good sandbox underneath.
