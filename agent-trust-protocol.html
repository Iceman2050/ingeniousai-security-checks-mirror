Agent to Agent Protocol: The Trust Spec

AI agents are starting to collaborate with each other — one agent delegating a refund to a finance agent, a research agent handing off to a visualization agent, a support agent calling a diagnostic agent built by a completely different vendor. Agents collaborating without verification is the next supply-chain hole: every delegation is a trust decision nobody logged. This is a readable specification for making that trust explicit.

What the Agent Trust Protocol is

An agent-to-agent protocol is a shared standard that lets AI agents built by different vendors, on different frameworks, discover each other, negotiate what they may do, delegate work, and exchange results — without custom integration code for every possible pairing. Google's A2A protocol (introduced April 2025, donated to the Linux Foundation in June 2025) is the best-known example: agents publish capability "agent cards," exchange task objects, and stream progress updates. Think of MCP as the wiring between an agent and its tools; A2A is the phone line between two working agents.

The Agent Trust Protocol builds on that idea with an explicit security layer: before any delegation happens, the agents verify each other through four steps — capability attestation, permission handshake, session binding, and an audit trail. It is a trust ceremony for machine-to-machine delegation.

The protocol flow, in plain English

Capability attestation
→
Permission handshake
→
Session binding
→
Audit trail
1

Capability attestation

The requesting agent presents a signed, machine-checkable statement of what it is and what it claims it can do: its identity, its tools, its data-access limits — cryptographically signed so the receiving agent can verify it was not tampered with. Think of it as showing ID and credentials at the door.

Plain English: "Here is who I am, here is what I can do, and here is proof I did not forge this."
2

Permission handshake

Both agents agree on a narrow, explicit scope for this one task — which actions are allowed, which data may be read, what is off-limits — and both record that agreement. The scope is the smallest set of permissions that completes the task. If the task needs more, a new handshake happens.

Plain English: "You may read these three files and write this one report. Nothing else. We both sign that."
3

Session binding

The agreed scope is locked into a time-limited session token that travels with every subsequent request. Any attempt to step outside the scope — a new tool, a wider data query, a longer-lived action — invalidates the binding and re-triggers the handshake. Permissions cannot quietly expand mid-task.

Plain English: "Your pass works for 15 minutes and only opens these doors. Try another door and the pass stops working."
4

Audit trail

Every delegation — who asked, who acted, what scope was granted, what was produced — is written to an append-only, hash-chained log. When something goes wrong, the full chain of who-did-what is reconstructable, step by step, back to the original requester.

Plain English: "Everything is written down in a ledger nobody can edit, so blame is traceable."

Worked example: the refund

A customer-support agent asks a finance agent to issue a $40 refund

  1. Attestation. The support agent presents its signed attestation: identity support-agent-7, tools: read_tickets, request_refund. The finance agent verifies the signature and checks the attestation issuer.
  2. Handshake. They agree: the finance agent may execute exactly one refund of up to $50 for ticket #8812, read-only access to that ticket's billing record, no access to other customers. Both record the agreement.
  3. Binding. A 10-minute session token encodes the scope. The finance agent issues the $40 refund. If it then tried to pull the customer's full payment history, the binding would fail and a fresh handshake would be required.
  4. Audit. The ledger records: support-agent-7 requested refund($40, ticket #8812) at 14:02; finance-agent-3 executed at 14:03 under session scope; both attestations and the handshake are linked. A later dispute resolves in minutes, not days.

Why this matters now

Multi-agent systems are shipping into production: orchestrators splitting work across specialist agents, agents from different vendors chained together, long-running delegations that stream progress for minutes or hours. Each delegation crosses a trust boundary — and today most of those boundaries are crossed on vibes: no attestation, no agreed scope, no binding, no audit trail. That is the next supply-chain hole. The protocol does not ask you to trust agents more; it gives you something checkable instead of trust.

What this spec does NOT cover

  • It does not guarantee how an agent's underlying model behaves inside its granted scope.
  • It does not resolve legal liability for what an agent does — no protocol assigns blame in court.
  • It does not do cross-company identity resolution (who vouches for an agent from another organization).
  • It does not promise instant revocation propagation across every participant.
  • It does not make models resistant to prompt injection or other input attacks.
  • It does not set human authorization thresholds — which actions require a human's approval is an operator decision, enforced by tools like an agent auth gateway.

A spec that pretends to cover these is selling something. This one names its boundaries.

Frequently asked questions

What is the agent to agent protocol?

An agent-to-agent protocol is a shared standard that lets AI agents built by different vendors and frameworks communicate and collaborate without custom integration code for every pairing. Google's A2A (April 2025, now under the Linux Foundation) is the best-known example, using agent cards for discovery, JSON-RPC messaging, and a task lifecycle. The Agent Trust Protocol adds an explicit security layer on that idea: capability attestation, permission handshake, session binding, and an audit trail.

How does the agent to agent protocol work?

In four steps: capability attestation (a signed, checkable statement of who the agent is and what it can do), a permission handshake (both sides agree a narrow scope for the task), session binding (the scope is locked into a time-limited session token; escalation re-triggers the handshake), and an audit trail (every delegation logged so the full chain is reconstructable).

What is the difference between A2A and MCP?

MCP (Model Context Protocol) is the wiring between an agent and its tools — often described as USB-C for AI tools. A2A is the line between two working agents — the networking layer for agent collaboration. One agent querying five systems needs only MCP; a workflow split across four specialist agents needs A2A too. They sit at different layers of the same stack.

Is the agent to agent protocol secure?

The protocol defines how agents authenticate, scope, and audit their collaboration — it does not make the underlying agents trustworthy. It cannot guarantee model behavior, prevent prompt injection in the models themselves, or assign legal liability. Security comes from applying the protocol strictly (narrow scopes, signed attestations, full audit trails) plus defense-in-depth around it, such as an agent authorization gateway.

What does the Agent Trust Protocol not cover?

It does not guarantee model behavior inside a granted scope; it does not resolve legal liability; it does not do cross-company identity resolution; it does not promise instant revocation propagation; it does not make models prompt-injection resistant; and it does not set human authorization thresholds — those are operator decisions. The spec names these boundaries explicitly above.
