The failure story: why direct API access breaks

  • Shared tokens kill accountability. One long-lived token across every laptop means the audit log says "the bot" — never which person asked, and never an answer you can defend.
  • The model can send raw queries. Left unsupervised, an agent can fire arbitrary queries or call generic http_request proxy tools that give it the whole API surface.
  • URLs may not require login. If the API is reachable on URLs with no authentication, the agent is the least of your problems — but it will find them.
  • Tool results can smuggle secrets. What an API returns can carry secrets straight into the next prompt the model sees.
  • No record of which tool ran for whom. Without per-call attribution, you cannot reconstruct what happened after an incident.

"The bot" is not a principal

A principal is the identity your API records and authorizes: a person who asked, or a service account for an overnight job. It can be granted, revoked, and explained in an audit. "The bot" can do none of those things. And chat-window OAuth proves who opened the chat — not which account each API call belongs to.

The three rules, in plain language

  1. The assistant calls a gateway — never the MCP server directly. The server sits on a URL only the gateway uses. Login, rate limits, and logs get one front door, and the model never touches the raw server.
  2. Every call runs as a named principal. No shared token passed around the team. Each request is attributable to a person or a service account, every time.
  3. The model sends what it wants — your code builds the search. Server-side validation (keyword allowlists, owner allowlists, result caps) decides what actually runs. "Be careful" in a prompt is just text; the server is the thing that must refuse.

Never expose a generic pass-through tool

A tool that takes method + path + body and forwards it to the API hands the model the entire API. Publish a short list of named functions instead — each one doing exactly one job, each one validated server-side.

AI Agents FAQ

Why is giving an AI agent direct API access dangerous?

A shared bot token destroys auditability — logs say "the bot" did it, not which person asked. The model may send raw queries, results can carry secrets into the next prompt, and there is no record of which tool ran for whom.

What is a principal?

The identity the API records and authorizes — a person who asked, or a service account for a scheduled job. "The bot" is not a principal: it cannot be granted, revoked, or explained in an audit.

What are the three rules for safe agent API access?

Call a gateway, not the MCP server directly; run every call as a named principal; validate input on the server — the model proposes, your code disposes.

Why not expose a generic HTTP proxy tool?

A pass-through tool (method + path + body) hands the model the whole API. Publish a short list of named functions instead, each validated server-side.

Is a demo gateway enough for production?

No. A tutorial gateway does not check everything — real deployments need identity providers and full audit trails.
