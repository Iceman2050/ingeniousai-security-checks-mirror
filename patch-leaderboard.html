Methodology — exactly how "days to patch" is measured

  • Days to patch = patch release date minus first public disclosure date (vendor advisory, CVE publication, or researcher disclosure — whichever came first).
  • Negative = patch shipped before public disclosure (patch-first — best practice).
  • 0 = coordinated same-day patch + advisory (standard practice among mature vendors).
  • Tiebreak: pre-patch in-the-wild exploitation window — days attackers had before any fix existed.
  • Honest caveats: this is an illustrative sample of 2026's biggest documented cases, not an exhaustive vendor census. Private notification dates are almost never public, so the clock starts at public disclosure. Exploitation-start dates are estimates from incident-response firms, not precise timestamps.

What the leaderboard actually teaches

Most mature vendors cluster at 0 — coordinated same-day patch and advisory is now the industry norm, which is good news. The real differentiators are patch-first behavior (Collabora's −33 days: the fix was out before the advisory told attackers where to look) and the pre-patch exploitation window (SonicWall's ~22 days, Ivanti's ~10 days, Langflow's no-fix-at-disclosure). When you evaluate a vendor, ask two questions: do they patch before they disclose — and how many days do attackers get before they do?

FAQ

Why do so many vendors score 0 days?

Because coordinated disclosure — shipping the patch and the advisory on the same day — is standard practice among mature vendors. A 0 is good: it means defenders and the patch arrived together. The leaderboard's real signal is in the exceptions: patch-first (negative) and unpatched-at-disclosure.

Is this an exhaustive ranking of all vendors?

No. This is an illustrative sample of 2026's biggest documented cases where both the disclosure date and the patch release date are publicly sourced. It is not a census of the software industry.

Why use public disclosure as the start of the clock?

Private notification dates are almost never published, so a vendor's true response time from first report is usually unknowable. Public disclosure is the first date attackers definitively have the information — that's the exposure window that matters to defenders.

How often is this updated?

With each major 2026 case that has both dates sourced. New entries are added newest-first with their sources linked.

What is a CVE checker?

A CVE checker is a free tool that tells you whether your software is affected by a published CVE — a publicly known cybersecurity vulnerability. It compares your version or configuration against the official advisory and gives you a patched, vulnerable, or unknown verdict in about 30 seconds.

How do I check if my software has a CVE?

Find your exact version number, then compare it against the vendor's security advisory or the NVD entry for the CVE. The fastest way is a CVE checker built for that product: paste your version and get an instant verdict against the published version tables.

How do I know if I am affected by a CVE?

You are affected when you run a vulnerable version and the vulnerable component is reachable or enabled — for example, open sign-ups, an exposed management port, or a vulnerable app installed. A CVE checker gives you the version verdict in seconds; the advisory's conditions tell you whether that verdict means real exposure.
