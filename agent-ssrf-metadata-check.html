Why are AI agents 2026 vulnerable to SSRF metadata attacks?

AI agents 2026 are vulnerable because their scraping tools fetch URLs from inside your cloud account, so a steered link to 169.254.169.254 or a private address returns metadata credentials and internal pages as ordinary content — unless a strict validator decodes and blocks the destination first.

The news: CVE-2026-112308 — crewAI's scraper skipped the private-address check

On October 19, 2026, CVE-2026-112308 was published: a High-severity SSRF vulnerability (CVSS 7.4, CWE-918) in crewai-tools through version 1.15.28. Its SeleniumScrapingTool never applied the validate_url private-address check, so an attacker who could influence agent tool input — the advisory names prompt injection as the steering path — could direct the tool's headless Chrome to loopback, RFC1918, or cloud metadata addresses and disclose internal data and cloud credentials.

Frequently asked questions

What is SSRF in an AI agent scraper?

Server-side request forgery (SSRF) in an AI agent scraper is when attacker-influenced input — often a prompt injection in a page, email, or document the agent reads — steers the agent's browsing or scraping tool to a URL the operator never intended, such as a cloud metadata endpoint or an internal admin service. The tool makes the request from inside your network or cloud account, so it can reach addresses that are unreachable from the public internet, and the response comes back to the agent as page content.

What is CVE-2026-112308?

CVE-2026-112308 is a High-severity SSRF vulnerability (CVSS 7.4, CWE-918) in crewAI's crewai-tools through version 1.15.28, disclosed October 19, 2026. Its SeleniumScrapingTool never applied the validate_url private-address check, so an attacker who could influence agent tool input — for example through prompt injection — could direct the headless browser to loopback, RFC1918, or cloud metadata addresses and disclose internal data and cloud credentials. Source: RedPacket Security CVE alert, labeled on this page.

Why is 169.254.169.254 so dangerous for agents?

169.254.169.254 is the link-local address of the cloud instance metadata service on AWS and several other clouds. A plain unauthenticated request to its meta-data paths returns temporary IAM role credentials for the machine the agent runs on. If a scraping tool loads that URL and returns the page text to the agent — exactly what scrapers are built to do — those credentials can be exfiltrated through the agent's own output.

Does this check fetch the URL I paste?

No. Nothing is fetched, ever. The classifier runs entirely in your browser: it parses and normalizes the URL string, decodes alternate IP encodings such as hex, octal, and single-integer forms, and applies a strict validator policy locally. It is a simulation of what a validator would decide, not a network probe — which is precisely why it is safe to paste internal or metadata URLs into it.

Why do hex, octal, and integer IP addresses bypass scrapers?

Because many validators only pattern-match the familiar dotted-decimal form. A browser, however, happily resolves alternate encodings of the same address: 0x7f.0.0.1, 0177.0.0.1, and the single integer 2130706433 are all 127.0.0.1. A validator that does not decode every encoding to the same 32-bit address before checking its ranges will wave the encoded forms through to exactly the loopback service it meant to block.

What should a strict URL validator for an agent tool check?

A strict validator should: allow only http and https; reject any URL with embedded userinfo; decode the host from every IP encoding (dotted, hex, octal, integer, and IPv6 including IPv4-mapped forms) and block loopback, RFC1918 private, link-local and metadata, CGNAT, and reserved ranges; block localhost and internal suffixes by name; re-validate after DNS resolution to defeat rebinding; and re-validate every redirect target, because the first URL being public says nothing about where it sends the tool next.
