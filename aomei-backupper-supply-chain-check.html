AOMEI's own update servers delivered a backdoor. Is it still on your machines?

Between May and July 2026, the cluster Google tracks as UNC7017 tampered with AOMEI Backupper's own update servers in 5–10 minute bursts — swapping two unsigned config files so any PC checking for updates in that window downloaded and ran a backdoor. No vulnerability exploited. No click needed. Organizations across 11 countries were hit, and AOMEI's server fix doesn't clean machines already infected. Five questions to check your exposure.

Short answer: if you run AOMEI Backupper (or its sibling AnyViewer, which shares the update flow) and haven't hunted for this, assume exposure until proven otherwise. The tampering windows were tiny — a client checking a minute before or after got clean files — so you can't reason your way out with timing. Hunt the April–July window, check the scheduled-task chain, and rebuild anything suspect from a clean installer.

Remediation: hunt it, then rebuild

1. Know where AOMEI lives in your fleet

Inventory every machine running AOMEI Backupper — and AnyViewer, which shares the update flow. You can't hunt what you haven't inventoried.

2. Hunt the April–July window

Preserve update files cached in the program's folders and correlate them with network logs from that period. The vendor's current download page shows only clean files now — history is what matters. Look for the scheduled task launching signed Radmin + planted DLL + SHINYROAD, and any Adaptix C2 masquerading as Nitro PDF.

3. Cut the exfil paths

Block the attacker infrastructure named in the reports, and block outbound SMB (TCP 445) and WebDAV to external addresses — that kills the NetNTLMv2 credential-theft technique outright.

4. Rebuild, don't just clean — then rotate

A server-side fix never touches an implanted machine. Rebuild affected hosts from a known-clean installer (fresh download, verified), and rotate every credential those machines held after rebuilding, in dependency order.

Frequently asked questions

What happened with AOMEI Backupper's update servers?

Between May and July 2026, attackers repeatedly altered two unsigned files on AOMEI's own update servers — down_html.ini and Notifycfg.ini — for five to ten minutes at a time. Any copy of AOMEI Backupper that checked for updates during a window downloaded and ran the attacker's package. Disclosed by Google Threat Intelligence Group, Mandiant, and ManageEngine's Threat Analysis Lab; attributed to the cluster GTIG tracks as UNC7017.

Was a software vulnerability exploited?

No. According to ManageEngine's lab, nothing in the software was exploited and no user action was needed beyond having the program installed and running. The updater never cryptographically verified the files it fetched — the checksum meant to prove the download genuine sat inside the same unsigned file that named it.

What malware was delivered?

The CROSSROAD downloader and the SHINYROAD implant, launched through a signed Radmin executable side-loading a planted DLL from the same directory via a scheduled task. Some machines also received Adaptix C2 disguised as Nitro PDF software. A July 20 change could also leak NetNTLMv2 authentication hashes through an invisible one-pixel WebDAV pop-up without running any program.

Did AOMEI fix it? Am I safe now?

AOMEI told Mandiant on July 29 that it took corrective action on its servers — but that fix does not remove the backdoor from machines already compromised. Neither report names which Backupper versions are affected, and ManageEngine said it had not independently confirmed containment. Infected machines remain compromised until investigated and rebuilt.

I run AOMEI Backupper — what should I do?

Hunt across April–July for compromise: preserve cached update files, review network logs, inspect scheduled tasks for the Radmin/DLL/SHINYROAD chain, block the attacker infrastructure and outbound SMB and WebDAV to external addresses, then rebuild affected machines from a clean installer and rotate credentials.
