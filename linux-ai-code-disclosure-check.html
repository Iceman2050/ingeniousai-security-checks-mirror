Linux just dropped AI-code disclosure. Should your project?

At the Linux kernel Maintainers Summit on October 8, 2026 in Prague, maintainers reached consensus to deprecate the "Assisted-by" tag — the disclosure previously expected when a kernel submission included AI/LLM-generated content. A message to the Linux mailing list announced the change and removed the tag's documentation. Linus Torvalds answered critics bluntly: banning AI-generated code is "utterly stupid" — like prohibiting compilers or text editors. His test is simpler and harder: does the contributor actually understand the code? If they can't demonstrate real understanding of what it does, the tool that wrote it is irrelevant. Meanwhile the industry is split: GCC, the compiler toolchain behind Linux itself, has drawn a hard line against AI-generated code. There is no consensus — which means your project needs its own deliberate policy, not a copy of someone else's. This 60-second check tests whether yours is sane. Free, no signup.

The sane policy, in five lines

  • Test understanding, not tools. The Torvalds principle: a contributor who can explain every line may use any tool; one who can't may use none. Make this the review standard.
  • Keep disclosure even if Linux dropped it. You don't have the kernel's reviewer bench. Disclosure tells reviewers where to look harder, and transparency rules (like the EU AI Act's AI-content obligations) are moving toward more disclosure, not less.
  • Scan AI-generated code adversarially. AI code fails in patterns — insecure defaults, hallucinated APIs, missing edge cases. Automated vulnerability scanning on AI-written contributions is the cheapest high-value control.
  • Inventory it. Tag AI-generated code in your repo metadata. When the next AI-specific vulnerability class emerges, you'll need to find it all in hours, not quarters.
  • Write it down. A policy nobody wrote down is a policy nobody follows. One page: allowed tools, disclosure rule, review standard, scanning requirement.
