The 60-second exposure check

Answer honestly for the repo you deploy to production. Weighted scoring — native-addon and lockfile controls carry the most weight.

1. Is a lockfile (package-lock.json, pnpm-lock.yaml, or yarn.lock) committed to the repo?
2. Are production dependencies pinned to exact versions (no ^ or ~ ranges)?
3. Does CI run npm audit (or equivalent) on every PR and block on criticals?
4. Do you review new transitive dependencies before adding a direct dependency?
5. Do you vet native addons (.node binaries, pre/postinstall scripts) before installing?
6. Do installs default to --ignore-scripts, with only allowlisted scripts permitted?
7. Do production builds use a private registry proxy or ship a software bill of materials (SBOM)?

What this check does NOT do

This page is an honest hygiene self-assessment, not a malware scanner. It cannot scan your node_modules for malicious code, cannot tell you whether a specific package version is compromised, and cannot replace npm audit, Socket, or a dedicated supply-chain scanner. It scores the controls that determine how exposed your tree is — nothing more.

Why install-time is the cybersecurity blind spot

  • The malware runs before your code does. imgdecode's shellcode loader lives in a Windows native addon — it executes during npm install, long before any import statement is evaluated.
  • Transitive dependencies multiply the surface. One direct dependency can pull dozens of transitive ones; any of them can publish a malicious patch release at any time.
  • Version ranges are silent doors. A ^1.2.3 range plus no lockfile means next month's install may resolve to a version the attacker published yesterday.
  • The wave is the signal. 1,500+ exposed packages in one week means this is systematic infrastructure abuse, not isolated typosquats.

Frequently asked questions

What is the October 2026 npm supply chain attack wave?

More than 1,500 npm packages were exposed in a single week ending October 17, 2026 — a wave of compromised, typosquat, and outright malicious packages reported across the ecosystem that week.

What is the MALFEX 'imgdecode' package?

imgdecode is a MALFEX-labeled malicious npm package reported by The Hacker News on October 17, 2026. It hides a shellcode loader inside a Windows native addon, so the malicious code runs at install time — not when the package's JavaScript is imported.

How do lockfiles protect against npm supply chain attacks?

A lockfile pins every dependency — direct and transitive — to an exact resolved version and integrity hash. Without one, a fresh install can silently pull a newer, compromised release published after your last good install.

Can this checker detect malware in my node_modules?

No — and it says so honestly. This is a hygiene self-assessment, not a scanner. It scores the controls (lockfiles, pinning, audits, script-blocking) that determine how exposed your tree is; to scan installed code, use npm audit, Socket, or a dedicated supply-chain scanner.
