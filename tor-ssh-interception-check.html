Cybersecurity News Today: Tor Exit Relays Redirected SSH Logins to Interception Servers

The network story in cybersecurity news today is about the last hop. A researcher scanning roughly 3,000 Tor exit relays on October 2 found 333 of them redirecting SSH connections to the same 12 interception servers. Anyone who then logged into their own server over Tor with a password, after accepting the host key the interceptor presented, handed that password over. The interceptor passed the session through to the real server, so nothing looked wrong, and later used the stolen passwords to test sudo rights and plant an installer. The relays were not run by the attacker. Their operators' hosts were compromised by Ebury, a long-running OpenSSH backdoor. The window is closed; the credential question it leaves behind is not.

Honest scope — read this first: Exposure needed three things at once: an SSH connection routed over Tor, between October 1 and the afternoon of October 5, using password authentication, with the user accepting the interceptor's host key. Key-based logins could not be relayed. The larger figure in the research, 377 relays by 59 operators, counts relays whose exit policy matched the attacker's pattern: a policy match, not proof that each relay was compromised or intercepting. No victim count exists, and this page does not invent one.

What the research found, step by step

  • The scan: researcher "kaba" tested about 3,000 exit relays on October 2 and found 333 redirecting SSH to 12 shared interception servers. Analysis of Tor directory data for October 1–4 counted 377 relays from 59 operators matching the attacker's exit policy, peaking at 7.46 percent of Tor's exit capacity on October 4.
  • The capture: the interceptor proxied the session to the real server. A captured password was later used to check for sudo access and to run a base64-encoded Perl installer; the operation had patience and a second stage.
  • The root cause: Ebury, an OpenSSH backdoor (this wave carried version 1.8.3) living on the relay operators' own hosts. ESET's long-running research counts roughly 400,000 servers infected between 2009 and 2023, with more than 100,000 still infected in late 2023.
  • The post-mortem that explains it: in the largest affected relay family, one password had been reused for the SSH login, for sudo, and as the backup passphrase, stored in plaintext, with password authentication enabled. The attacker was in on August 28 and had root in about five minutes.
  • The response: the Tor Project began BadExit and MiddleOnly voting at 18:00 UTC on October 4; the relays entered the consensus flagged by 21:00, and by 17:00 UTC on October 5 no relay with the attacker's policy remained. The exit-flag relay count fell by about 370 across October 3–5 and had not recovered by October 18.

The arithmetic deserves one plain sentence: at its October 4 peak, the pattern covered 7.46 percent of Tor exit capacity, which for a person administering a server over Tor that week was close to a one-in-thirteen chance per exit of meeting an interceptor. The defense that mattered was not luck. It was whether the login used a key instead of a password.

Why this cybersecurity news today matters: the password is the weak hop

Tor did what Tor promises: it hid where the connection came from. It cannot vouch for where the connection ends. An exit relay is a stranger's machine by design, and this incident shows what a compromised stranger can do with an SSH session that authenticates by password: keep it, replay it, escalate it. Key-based authentication survived the same interception untouched, because a signature cannot be lifted out of one session and used in another. The other lesson sits one layer down. The relay operators were not careless hobbyists; their hosts carried a backdoor that has survived since 2009, and in the best-documented family a single reused password turned a foothold into root.

The interception check: fingerprint and exposure test

Two parts. If your SSH client recorded a host key for a connection made over Tor during the window, paste its SHA256 fingerprint below (it lives in your known_hosts data or the warning you saw). Everything runs in your browser; nothing is sent anywhere.

Run the response steps

  • Rotate what the window touched: any password used for an SSH login over Tor between October 1 and 5 gets changed, from a clean machine over a normal connection. If that password was reused anywhere (the post-mortem pattern), change it everywhere.
  • Go key-only: install key authentication, then disable password authentication on your servers. This incident could not relay a key login; make that permanent.
  • Verify host keys out of band: never accept a changed host key on trust. Compare the fingerprint through a second channel (provider console, a colleague, your records) before typing anything.
  • Operators: hunt Ebury on the host: look for a setuid /usr/lib/x86_64-linux-gnu/libkeyutils.so.1.10.2 owned by no package, the libkeyutils.so.1 symlink pointed at it, the abstract socket @event-0YsOG9WSOE, a fake /sbin/rsyslogd inside the ssh.service cgroup, and any link to 185.225.226.62. Check torrc for ExitPolicy changes and NAT rules on port 22, plus unknown users, keys and cron entries.
  • If Ebury is present, rebuild, do not clean: take the host offline, preserve the disk and logs, reinstall from clean media (the implant survived reboots), start a new relay identity, and rotate every credential the host ever held. Never type a password into a suspect server: Ebury captures it locally too.
  • Audit the targets: on servers you administer, review authentication logs for the window and after it: new authorized_keys entries, new users, unexpected sudo. A stolen password's second stage arrived later, not during the session.

Frequently asked questions

What is the Tor SSH interception case, in plain terms?

The Tor SSH interception case is the October 2026 discovery that hundreds of Tor exit relays had been quietly redirecting SSH connections to a set of interception servers. Anyone who logged into a server over Tor with a password, after accepting the interceptor's host key, could have that password captured and reused. The relays' own hosts were compromised by the Ebury OpenSSH backdoor; the Tor Project removed the relays from the network by October 5.

Could the interceptors steal SSH keys too?

No, and the reason is structural. SSH key authentication proves identity with a signature bound to that specific session, so an interceptor sitting between you and the server cannot replay it to the real server. Password authentication has no such binding: type the password into the wrong endpoint and the interceptor owns it. That is why the exposure test for this incident is Tor plus password plus an accepted host key, and why moving servers to key-only login removes this whole class of attack.

How do I check a session or a server against this incident?

For a session: compare the fingerprint of the host key your SSH client recorded for connections made over Tor between October 1 and 5 against the published interceptor fingerprint, SHA256:6baCZCPsl+AfQuujUS81fMEE/C7UeJ+AwjrImqmDB3E. It is one of possibly several interceptor keys, so a match is proof and a non-match is not clearance. For a relay or server host: look for the Ebury signs listed on this page, including the setuid libkeyutils file no package owns and the fake rsyslogd process. A clean host check does not rule Ebury out.

I run a Tor relay. What should I do?

Check your torrc for ExitPolicy or ExitRelay changes you did not make, look for NAT rules touching port 22, and audit for unknown processes, users, SSH keys and cron entries. Then check the Ebury artifacts: a setuid libkeyutils.so.1.10.2 owned by no package, the library symlink pointed at it, the abstract socket named in the research, and connections involving 185.225.226.62. If the host is compromised, take it offline, preserve the disk and logs, reinstall from clean media, start a new relay identity, and rotate every credential the host ever held.

Was I a victim of the interception?

Nobody can tell you from a list, because no victim count exists. Run the three-part test instead: did you connect to a server by SSH over Tor between October 1 and 5, did that login use a password, and did you accept a host key during it? If all three are true, treat the password as captured and rotate it from a clean machine over a normal connection, whether or not the one published fingerprint matches. If you used key-based authentication, the interception could not relay your login.
