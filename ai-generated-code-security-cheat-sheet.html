What flaws does vibe coding output usually contain?

Coding assistants optimise for code that runs, not code that resists attack, so the same flaw families recur across projects and languages. Hardcoded secrets, injection sinks, dynamic execution on untrusted input, disabled TLS verification and insecure defaults appear again and again, because the training examples the models learned from contained them too.

  • 1. Hardcoded secrets: API keys, tokens and passwords written straight into source or config-shaped code.
  • 2. Injection flaws: SQL, command and template injection where user input reaches a sink unsanitised.
  • 3. Cross-site scripting: unescaped output rendered into pages, especially in quick demo front-ends.
  • 4. Dangerous dynamic execution: eval(), exec(), shell=True and unsafe deserialisation on data the program does not control.
  • 5. Disabled security defaults: verify=False, unverified TLS contexts, CSRF exemptions, permissive CORS added 'to make it work'.
  • 6. Over-broad permissions: wildcard IAM, public storage buckets and admin-scoped tokens chosen because they never error.
  • 7. Missing auth checks: endpoints that work beautifully in the demo because nothing verifies who is calling.

What is the 4-command sweep?

  1. Secrets: grep the repo for key-shaped strings (sk-, AKIA, ghp_, xox prefixes). Any hit: rotate first, then remove.
  2. Credentials in code: grep for password, passwd, api_key and secret assigned to quoted values, excluding obvious placeholders.
  3. Dynamic execution: grep for eval(, exec(, os.system, shell=True and unsafe YAML loads; check what input reaches each one.
  4. Disabled defaults: grep for verify=False, unverified contexts, StrictHostKeyChecking no and csrf_exempt. Each hit is a hole with a comment-shaped excuse.

Run the sweep after every AI-assisted coding session, not once per release — the flaws arrive per session, so the check has to as well.

How do you review an AI-written diff?

  • Read the diff, not the demo: working output proves the happy path only.
  • Chase every new network call, file write and permission the diff introduces — assistants add capabilities silently.
  • Ask what the code does with hostile input — empty, enormous, malformed and malicious are the four test cases.
  • Keep the sweep in CI so a future session cannot reintroduce a fixed flaw unnoticed.

Frequently asked questions

What is vibe coding security?

Vibe coding security is the practice of checking AI-generated code for the flaws models commonly introduce: hardcoded secrets, injection flaws, cross-site scripting, disabled TLS verification and insecure defaults. Veracode's 2025 GenAI Code Security Report found 45 percent of AI-generated code shipped a real vulnerability, so review is not optional.

How do I check AI-generated code for leaked API keys?

Search the repository for key-shaped strings — the sk-, AKIA, ghp- and xox- prefixes cover the common providers — and for password or api_key assignments with quoted values. Any real hit must be rotated immediately, because a committed key is a compromised key even if the commit is later deleted.

Is a grep sweep enough to secure AI-written code?

It is the right first pass, not the whole job. The sweep catches the mechanical families — secrets, dynamic execution, disabled defaults — quickly and repeatably. Judgment flaws like missing authorisation checks and broken business logic still need a human or a deeper scanner reading the code in context.
