What is prompt injection?

Prompt injection is an attack where untrusted content — a file, web page or repository — contains instructions that an AI agent follows as if its user had given them. When those instructions make the agent edit a shell startup file, the attack gains persistence: the planted line keeps running at every login, on every new terminal, whether or not the agent is ever used again.

The October 2026 hook: CVE-2026-55607

According to the advisory as briefed for this check, CVE-2026-55607 describes a worktree sandbox escape in Claude Code disclosed on October 15, 2026. A worktree sandbox is meant to confine an agent to a checkout of one repository. An escape breaks that confinement, so files outside the repo — including the startup files in your home directory — can be modified. The advisory's own remediation was strikingly manual: open ~/.zshenv and look for lines you did not write. This page turns that hand-check into a repeatable diff.

The manual checklist: files and patterns

Inspect these 7 locations — 6 startup files plus your crontab:

  • ~/.zshenv — read by every zsh invocation, including scripts; the file the CVE-2026-55607 advisory named first.
  • ~/.zprofile and ~/.zshrc — login and interactive zsh startup.
  • ~/.bashrc, ~/.bash_profile and ~/.profile — the bash and POSIX equivalents.
  • Your crontab — run crontab -l and look for entries you did not schedule.

Grep for these suspicious patterns in each file:

  • Downloads executed directly: a curl or wget command piped into sh, bash or zsh.
  • Encoded payloads: base64 with decode flags, or long opaque encoded strings.
  • Dynamic execution: the eval keyword applied to a variable, or command substitution running downloaded content.
  • Command shadowing: an alias redefining ls, git, cd or sudo.
  • Loader and environment hijacks: exports of LD_PRELOAD, DYLD_INSERT_LIBRARIES, BASH_ENV or ZDOTDIR.
  • Repository sourcing: a source or . line pointing inside a repo, a relative path, or /tmp.
  • Path hijacks: a new PATH entry prepended from a repository or temporary folder.

Example sweep: grep -nE 'curl|wget|base64|eval|LD_PRELOAD|BASH_ENV|ZDOTDIR|source|\.' ~/.zshenv ~/.zshrc ~/.bashrc — then judge every hit against what you remember writing.

Frequently asked questions

Why can coding agents touch your dotfiles at all?

Coding agents run with your user account's file permissions, and shell startup files live in your home directory, outside the repository they were asked to edit. A sandbox is supposed to fence the agent into a worktree, but CVE-2026-55607 showed a worktree escape could break that fence, letting instructions from an untrusted repo reach files the user never opened.

What does a planted dotfile line actually look like?

A planted line usually runs code at every shell startup: a download piped straight into a shell, a decoded blob being executed, an alias that quietly shadows a common command like ls or git, a PATH entry pointing inside a repository, or a source line loading a script from a folder you do not control. It hides among your real settings.

What should you do if you find a planted line?

Do not just delete it and move on. Save a copy of the file for evidence, remove the line, then assume anything that ran at startup had your privileges: rotate exposed credentials and tokens, review recent shell and account activity, and check your crontab and other startup files too, because one planted line rarely travels alone.

How do you snapshot your dotfiles before the next agent run?

Before the run, copy each startup file into a dated snapshot folder outside any repository, or commit them to a private dotfiles repo so changes show up as a diff. After the run, compare the live files against that snapshot with the tool above. Two minutes of copying turns a forensic question into a yes-or-no answer.
