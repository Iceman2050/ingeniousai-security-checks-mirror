State of MCP Security 2026: the negotiation layer nobody can see

We ran protocol-handshake probes against 27 public, hosted MCP endpoints — Microsoft, AWS, GitHub, Stripe, Figma, Cloudflare, Linear, Notion, Slack and more — asking each one to negotiate four real protocol eras and two fictional ones. The results say less about any single vendor and more about the ecosystem: the negotiation layer is unobservable for most servers, and the ones we could see downgrade you quietly.

What "silent downgrade" means here

We asked for the newest protocol era, 2026-07-28. The server answered with 2025-06-18 — an older era — without declaring the downgrade. Your client thinks it's speaking the newest protocol; it isn't. A silent downgrade may be a compatibility choice, but it is one you should see, not discover in production when a new-era feature silently doesn't work.

Both downgrading endpoints (Microsoft Learn, AWS) also answered fictional eras (1999-01-01, 2037-12-31) with their default version instead of rejecting them — the version field is not validated.

Why most servers are unobservable

Twenty endpoints — GitHub, Stripe, Figma, Linear, Slack, Notion, Cloudflare, HubSpot, Atlassian, Supabase, Sentry, Neon, Vercel, Monday.com, Ahrefs, Perplexity, Semrush, Exa, X API, X Docs' authenticated paths — require OAuth before answering any handshake. That's reasonable access control, but it has a side effect the ecosystem hasn't reckoned with: independent researchers cannot verify negotiation behavior at all. The October 2026 public probe of 78 endpoints (85% silent downgrades) was retracted partly because the stateless 2026-07-28 spec removed the handshake — the instrument gap is real, and OAuth walls make it wider.

Methodology (so you can check our work)

Run date: 2026-10-17. Tool: mcp-negotiation-prober (open source, MIT) — sends an MCP initialize handshake with protocolVersion set to each of 6 eras (2024-11-05, 2025-03-26, 2025-06-18, 2026-07-28, plus fictional 1999-01-01 and 2037-12-31) and classifies the echoed version. No credentials were used and none were needed: every probe was an unauthenticated handshake. Endpoints were taken from vendors' own published docs (Microsoft Learn, Linear, Stripe, Figma docs; the Skyvia Oct 2026 roundup; vendor changelogs). An endpoint was included only if it responded to probes at all (HTTP response, including 401). Verdicts describe negotiation behavior only — a silent downgrade is not a vulnerability, and UNKNOWN is not a finding of wrongdoing. Results are reproducible: same tool + same endpoints = same verdicts.

What this means for you

If you run agents against hosted MCP servers: pin and log the negotiated protocol version per session, not the requested one; treat OAuth-walled servers as unobservable and demand version-transparency from vendors; re-run negotiation checks after vendor updates — the downgrade you don't see is the behavior change you can't explain.
