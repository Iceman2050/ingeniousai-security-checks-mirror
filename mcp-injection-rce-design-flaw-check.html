Why this disclosure matters beyond one setup

  • The flaw is architectural, not a typo. Any MCP deployment where untrusted tool output can reach a privileged executor shares the shape — the model’s system prompt cannot fix it.
  • Hints are not controls. A client-side destructiveHint is a suggestion the model may honor or ignore. Attackers count on the “ignore” branch.
  • Agent tool calls are camouflage. The disclosure notes there is no malware to detect — logs look like normal agent tool calls, so the intrusion hides in legitimate-looking activity.
  • Credentials ride along by default. Full environment inheritance means the attacker doesn’t exfiltrate one key — they inherit your AWS keys, GitHub tokens, and SSH identities in one move.
  • Persistence is built in. ~/.ssh/authorized_keys, cloud IAM keys, cron jobs, shell profiles: a successful injection doesn’t just run once, it stays.

Frequently asked questions

What is the “WTF is MCP?” disclosure?

“WTF is MCP?” is a security disclosure published October 18, 2026, describing a critical prompt-injection-to-remote-code-execution design flaw in an MCP-based AI agent architecture. The core problem is a missing trust boundary: untrusted web content is analyzed by one tool and then fed to a privileged command-execution tool, letting attacker-controlled text cross into code execution with the agent’s full environment and credentials.

How does the prompt-injection-to-RCE chain work?

Per the disclosure: a web-analyzer tool dumps injected text from an attacker-controlled web bundle, GitHub issue, blog post, PDF, or comment into the agent’s context, and a privileged tool then executes commands. Because the agent inherits the user’s full environment, that means AWS keys, GitHub tokens, and SSH identities — plus persistence via SSH authorized_keys, cloud IAM keys, cron jobs, and shell profiles.

What does “destructiveHint is not a security control” mean?

In the disclosed architecture, warnings about destructive commands existed only as a client-side destructiveHint — a suggestion to the model, not an enforced control. The disclosure’s point: a hint that the model may or may not honor is not a security boundary. Real protection needs server-side enforcement — sandboxing, capability isolation, and explicit approval — not text asking the model to be careful.

Is this a prompt-engineering bug or an architecture problem?

The disclosure argues it is an architecture problem, not a prompt-engineering bug: a capability-isolation failure. The architecture lets untrusted web text cross into command execution, inherits the user’s full environment, and relies on a client-side warning as its only guardrail. Any deployment with the same shape has the same flaw, regardless of the model’s system prompt.

How do I fix an MCP deployment shaped like this flaw?

Mark all tool output from untrusted sources as untrusted and never let it flow into command execution. Run command-execution tools with minimal environments and no inherited secrets. Enforce destructive-action approval server-side, not via client-side hints. Isolate web-analysis tools from privileged executor tools, sandbox the agent, and log every tool call so an injection chain is visible.
