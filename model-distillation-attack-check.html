What is a model distillation attack?

A model distillation attack is the systematic extraction of a model's behaviour through its normal API: an attacker sends large numbers of carefully structured prompts, records the outputs, and uses those input–output pairs to train a cheaper copy of the model. A distillation attack is theft of behaviour, carried out one legitimate-looking request at a time.

The gateway-log checker for AI agents 2026

Paste JSONL — one JSON object per line — from your API gateway or provider logs. Recognised fields: timestamp, api_key_id, model, prompt_len, topic, completion_tokens and prompt_prefix (all optional except a key id; aliases like api_key, prompt_length and ts also work). The checker groups requests by key and scores five signals per key:

  • Topic-coverage sweep — one key covering an unusually broad spread of topics, the signature of behaviour harvesting rather than a product workflow.
  • Paraphrase clusters — many near-identical prompt lengths, consistent with the same probe rephrased again and again.
  • Monotonic parameter sweeps — prompt length walking steadily upward in time order, a staircase probing of the model's response surface.
  • Extraction pacing — machine-regular timing at a fast median interval, measured against the key's own rhythm rather than a global threshold.
  • Shared prompt prefixes across keys — the same prompt scaffold appearing under 2 or more keys, the classic sign of one operator splitting an extraction across keys to stay under per-key limits.

Request volume alone scores zero points. A busy, narrow, irregular key is a customer; a systematic key is a suspect.

How distillation differs from ordinary abuse and scraping

Ordinary API abuse is usually about volume for its own sake: credential stuffing, free-tier farming, resale of raw access, or a runaway script. Scraping is about content: pulling pages or data out. Distillation is different in intent and in shape. The goal is the model's behaviour itself — a training set that transfers capability to a rival model — so the traffic is designed for coverage: every topic, every style, every edge of the response surface, probed evenly and repeatedly. That is why distillation survives spend dashboards and rate totals that catch cruder abuse, and why per-key pattern analysis — topic breadth, paraphrase clustering, staircase sweeps, pacing regularity, cross-key prefixes — is the detection layer that actually sees it.

Immediate defences: what to do today

  • Per-key rate limits and concurrency caps. Extraction needs volume and speed. Per-key pacing limits are the single highest-leverage control — they stretch a 48-hour harvest into weeks and make it visible.
  • Topic-sweep alerts. Alert when one key's topic breadth in a short window looks nothing like its own history. Legitimate keys are narrow; sweeps are not.
  • Key rotation and re-verification. Rotate any suspect key immediately and require the account behind it to re-verify before new keys are issued — otherwise the operator just mints a fresh key and resumes.
  • Watch for split operators. Correlate prompt prefixes and scaffolds across keys. Per-key limits fail silently when one operator runs 5 keys in parallel.
  • Keep per-request logs. Billing aggregates cannot detect this. Retain timestamp, key, model, prompt length/topic and completion tokens per request — the five fields this checker needs are the five fields your alerting needs.

Frequently asked questions

How do I know if my API is being distilled?

Look at behaviour per API key, not totals. Distillation leaves a pattern: one key sweeps systematically across many topics, sends clusters of near-identical prompt lengths (paraphrase probing), walks a parameter such as prompt length or requested tokens up in a steady staircase, fires at machine-regular intervals, and sometimes shares the same prompt prefix across several keys. Paste your gateway logs into the checker on this page: it scores exactly those signals per key and returns CLEAN, WATCH or DISTILLATION-SUSPECT with the fired signals named.

Is high usage the same as distillation?

No. A busy legitimate customer is high-volume but narrow: a few topics, varied prompt shapes, human-irregular timing, one product workflow. A distillation run is high-volume and systematic: broad topic coverage, repeated near-identical probes, staircase parameter sweeps and regular pacing. Volume alone proves nothing — that is why this checker scores zero points for request count by itself, and why a key with modest volume can still be DISTILLATION-SUSPECT if its pattern is systematic.

What should I throttle first if I suspect distillation?

Throttle the suspect key, not your whole API. First, cut that key's rate limit and concurrency to near zero while you review — extraction needs volume and speed, so pacing limits hurt it most. Second, alert on topic-sweep behaviour: a single key touching an unusual breadth of topics in a short window. Third, rotate the key and require re-verification of the account behind it. Do not start by raising prices or throttling everyone: that punishes legitimate customers and barely slows a determined extractor.

Can I detect a distillation attack from billing alone?

No. Spend dashboards show how much a key consumed, aggregated over time — they miss the pattern entirely. A distillation run can be spread across several keys and kept under spend alerts on each one, and a legitimate power user can outspend an extractor while doing nothing wrong. Detection needs per-request log structure: topics, prompt lengths, timing and prefixes per key. Billing tells you the size of the fire after the fact; log patterns are the smoke detector.
