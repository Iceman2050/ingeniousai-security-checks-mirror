Cybersecurity News Today: Eight eMudhra CA Keys Compromised — Is Your Chain Still Trusted?

The most consequential story in cybersecurity news today is not a breach of a website — it is a breach of the system that decides which websites to trust. The private keys of eight intermediate certificate authority (CA) certificates belonging to eMudhra — the Indian CA that sells certificates under the emSign brand — are compromised, Mozilla and Google's Chrome Root Program confirmed on October 20, 2026. Whoever holds an intermediate CA key can mint a certificate for any website that browsers would accept. Chrome and Firefox blocked the certificates within hours of the October 17 report. The rest of the software world only caught up on October 20 — and only where someone actually installs the update.

Honest scope — read this first: There is no evidence of rogue certificates. Chrome verified that no TLS certificate chaining to the six web intermediates had been logged to Certificate Transparency before its block landed, so none could have been trusted by default in Chrome or any other CT-requiring browser. If you only browse the web in Chrome or Firefox, you need to do nothing — the revocations were pushed to you automatically. The real exposure sits elsewhere: non-browser software that never checks revocation, and legitimate websites whose certificate chains run through eMudhra's emSign roots, which several trust stores have now removed entirely.

The eight certificates, exactly as listed

  • TLS, domain validated: EM DV TLS CA - G3B (eMudhra BV, Netherlands) and EM DV TLS CA - G3C (eMudhra Inc, United States).
  • TLS, organization validated: EM OV TLS CA - G3B and EM OV TLS CA - G3C.
  • TLS, extended validation: EM EV TLS CA - G3B and EM EV TLS CA - G3C.
  • Code signing: EM OV CS CA - G3B and EM OV CS CA - G3C. (Chrome did not need to block these two for web traffic — its TLS verifier will not build a path through an intermediate restricted to code signing.)

Six of the eight compromised intermediates — 75 percent of the set — exist to sign website certificates; the remaining two sign code. The six TLS intermediates were issued by emSign Root TLS CA - G3 and chain to emSign ECC Root CA - G3, a root that sat in the Chrome and Apple root stores and, until October 20, in Mozilla's. Each of the eight also exists as a cross-signed copy under Sectigo's AAA Certificate Services root; Chrome's block matches the public key, so it catches the cross-signed copies too. The compromise was reported on the evening of October 17 by a researcher credited by Mozilla only as Wayne, who proved possession by signing a message with each of the eight keys. How the keys left eMudhra — and when — is not known. eMudhra has revoked all eight certificates.

Why this cybersecurity news today matters: browsers moved in hours, software stores moved in days

The browser response was the fast part. Chrome's CRLSet block was live 100 minutes after the report arrived; Mozilla finished pushing its OneCRL block to standard Firefox installations by 22:59 UTC the same evening. Apple blocked the certificates on October 19 and Microsoft on October 20. None of this required a browser update or a restart — revocation lists are fetched automatically. That machinery is exactly what the rest of the ecosystem lacks. A Go binary, a Python script using certifi, or a Rust program using webpki-roots carries its own bundled root store and typically never checks revocation at all: it keeps trusting a chain until the bundle changes. That is why the October 20 fixes matter more than the browser blocks — and why they only protect you if you install them, and, for Go, rebuild with the new release.

The fixes, and what each one actually does

  • Go 1.27.3 and 1.26.10 (October 20): the standard library now rejects any chain containing one of the eight keys (tracked as CVE-2026-111943), with no setting to turn it off. Programs pick it up only when rebuilt; Go 1.25 and older are out of support and get no fix.
  • Firefox 158.0.1 (plus ESR 115.43.1 and 153.5.1): carries the OneCRL block for installations that cannot receive Remote Settings (CVE-2026-113470). Standard Firefox installs were already protected by the October 17 push.
  • NSS 3.131.1: removes emSign ECC Root CA - G3 from the trusted list outright.
  • Python certifi 2026.10.19 and Rust webpki-roots 1.0.10: drop emSign ECC Root CA - G3 from their bundles. Homebrew's ca-certificates package does the same and also drops emSign Root TLS CA - G3 and AAA Certificate Services by public key.
  • Still pending as of October 20: Node.js (a draft change would block the eight keys) and Composer's ca-bundle (an open change would remove the root).

Note the split in approach: key-blocking (Chrome, Go) surgically rejects the eight compromised keys, while root removal (NSS, certifi, webpki-roots) cuts off every certificate chaining to the emSign root — including perfectly legitimate ones. Mozilla, which removed the root from NSS, acknowledged some servers will become unavailable to users of its trust list until those servers move to new chains. Chrome has also said it will remove emSign ECC Root CA - G3 in version 43 of its root store and is reviewing eMudhra's other root, emSign Root CA - G1.

Run the certificate-trust check now

  • Check your site's chain: view your certificate in a browser or run openssl s_client -connect yourdomain:443 -showcerts and read the issuer names. Any EM DV/OV/EV TLS CA - G3B or - G3C intermediate — or a chain topping out at emSign ECC Root CA - G3 or emSign Root TLS CA - G3 — means you are affected.
  • If you are an eMudhra/emSign customer: re-issue under a new chain now. Your current certificate was not necessarily abused — but root removals mean it will progressively stop being trusted by updated software.
  • Update software trust stores: rebuild Go services on 1.27.3 / 1.26.10; update Python environments to certifi 2026.10.19+; update Rust builds to webpki-roots 1.0.10+; take NSS 3.131.1 and Firefox 158.0.1 where you manage them.
  • Audit the quiet clients: internal tools, mobile apps, embedded agents, and CI jobs that pin their own root bundles do not receive browser revocation pushes. Inventory them; they are where a compromised intermediate stays trusted longest.
  • End users: do nothing in Chrome or Firefox — and treat any pop-up, email, or download offering a "certificate fix" as scam bait. The real fixes ship through your browser and your software's normal update channels, never through a download link in a message.

Frequently asked questions

What is the eMudhra CA key compromise, in plain terms?

The private keys of eight eMudhra intermediate certificate authority (CA) certificates were compromised: the EM DV, OV, and EV TLS CA - G3B and - G3C certificates, plus two code-signing intermediates (EM OV CS CA - G3B and - G3C). A researcher reported the compromise to the browser root programs on October 17, 2026, proving possession of the keys by signing a message with each one. How the keys left eMudhra, and when, is still unknown. eMudhra has revoked all eight certificates.

Am I at risk browsing in Chrome or Firefox?

Very low. Chrome received the report at 18:05 UTC on October 17, 2026 and had a CRLSet update blocking the six TLS intermediates by 19:45 UTC; Mozilla finished pushing its OneCRL block to Firefox by 22:59 UTC the same evening. Both browsers fetch these revocation lists automatically — no update or restart was needed. Chrome also confirmed that no TLS certificates chaining to the six web intermediates had been logged to Certificate Transparency before the block, so none could have been trusted by default in Chrome or other CT-requiring browsers.

How do I check if my website uses an affected certificate chain?

Inspect your site's certificate chain: in a browser, open your site, view the certificate details, and read the issuer chain; from a terminal, run openssl s_client -connect yourdomain:443 -showcerts and read the issuer names. If any intermediate is named EM DV TLS CA - G3B or - G3C, EM OV TLS CA - G3B or - G3C, or EM EV TLS CA - G3B or - G3C — or the chain tops out at emSign ECC Root CA - G3 or emSign Root TLS CA - G3 — your chain is affected and you should re-issue under a new chain. Free chain visualizers such as SSL Labs' SSL Test show the same issuer names.

Which software updates fix the trust stores?

Fixes released October 20, 2026: Go 1.27.3 and 1.26.10 reject any chain containing one of the eight keys (CVE-2026-111943), but Go programs only pick this up when rebuilt, and Go 1.25 and older get no fix. Firefox 158.0.1 (and ESR releases) carries the OneCRL block for installations that cannot receive Remote Settings (CVE-2026-113470). NSS 3.131.1 removes emSign ECC Root CA - G3 from its trusted list; Python's certifi 2026.10.19 and Rust's webpki-roots 1.0.10 drop the same root from their bundles. Node.js and Composer fixes were still pending as of October 20.

What should eMudhra and emSign customers do now?

Re-issue your certificates under a new chain that does not pass through the eight revoked intermediates or the emSign ECC Root CA - G3 root. Several trust stores (NSS, Python certifi, Rust webpki-roots, Homebrew ca-certificates) removed that root entirely rather than blocking only the compromised keys, and Mozilla has removed it from NSS — so even a legitimate certificate chaining to that root will stop being trusted by software using those stores until the site moves to a new chain.
