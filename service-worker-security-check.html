SERVICE WORKER SECURITY

Your service worker sees every request your site makes. Is it locked down?

A service worker is a JavaScript file that runs in the background, separate from your page — intercepting network requests, managing caches, and powering offline apps, background sync, and push notifications. Here is the part every developer should sit with: it can intercept, read, and rewrite every request inside its scope. A compromised or careless service worker is a man-in-the-middle on your own site — rewriting responses, skimming data, or serving stale or poisoned content long after you fixed the server. This 60-second check tests whether yours is an asset or a liability. Free, no signup.

Why a service worker is a security surface (verified against MDN):
• It runs in a worker context with no DOM access — but full power over navigation and resource requests in its scope, which it can intercept and modify at will.
• It only runs in secure contexts: HTTPS in production, with localhost treated as secure for development. (The spec is strict here because a network attacker who could inject a worker script would own the origin.)
• The script must be same-origin — an attacker can't register a worker from their own domain. They need script execution on yours (XSS) or a compromised server/CDN.
• Updates are byte-compared: a new script installs in the background but stays waiting until old pages close — unless you handle skipWaiting() / clients.claim() deliberately. Sloppy update handling = users stuck on old or poisoned content.
• Anything you cache is readable by any script on your origin — Cache Storage is not a vault. Cached sensitive responses widen every future XSS.

Service-worker hardening checklist

  • Scope it tight. Register at the narrowest scope that works. A root-scope worker sees every request on the origin — only grant that if the whole site genuinely needs offline behavior.
  • Version everything. Name caches per release (app-v3, not app), delete old caches in the activate handler, and handle the update flow explicitly instead of hoping users close all tabs.
  • Cache by resource type. Cache-first for hashed static assets; network-first or stale-while-revalidate for HTML and APIs; network-only for authenticated content. Never cache opaque error responses as content.
  • Treat the worker script like server code. Minimal logic, reviewed changes, pinned imports — a compromised importScripts() dependency inherits full request-interception power.
  • Defend the origin. Because registration requires same-origin script execution, your XSS defenses, Content Security Policy, and supply-chain hygiene are your service-worker defenses too.
  • Rehearse the kill switch. Keep a known-good page that unregisters workers, document the DevTools removal path, and make sure more than one person on the team knows it.
