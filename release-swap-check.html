The common payload shape is what this page scans for. What is a release swap?

A release swap is the replacement of a legitimate software release with a tampered one under the same name and version — through a hijacked maintainer account, a compromised build pipeline, or a registry weakness. It differs from a malicious package, which is bad from its first upload: a swapped package has a real history, real users and a real reputation, all of which the attacker inherits. Detection therefore cannot rely on the package's name or popularity; it has to read what the specific artifact does at install time, which is why the scanner below works on the code, not the brand.

Already installed a suspect release? Do this now

If the scanner flags code you have already installed or updated to, work this list in order — the install already ran, so the machine is the incident now:

  1. Stop further installs. Pause CI and deployment pipelines pulling the suspect version, and pin the last known-good release everywhere.
  2. Rotate credentials in exposure order. Cloud keys first, then SSH keys, then package-registry and GitHub tokens — the exact set October 2026's swapped releases were built to steal.
  3. Compare the artifact. Diff the installed release against the maintainer's source repository at the same version tag. A swap shows as code present in the artifact and absent from the source.
  4. Hunt for persistence. Review cron entries, services, shell startup files and autostart locations on every machine that installed it. Deleting the package does not remove what it registered.
  5. Check the accounts. Review cloud, GitHub and registry audit logs for the exposure window: new keys created, unfamiliar logins, unexpected publishes.
  6. Change the default. New releases land in a sandbox first, installs pin versions and verify hashes, and install hooks get read before they run — the scanner above takes under a minute per package.

Frequently asked questions

What is a release swap?

A release swap is when the artifact you install under a trusted name and version is not the artifact the maintainer built — it was replaced through a hijacked account, a compromised pipeline or a registry weakness. The name, version and download page all look correct; only the code changed. LiteLLM 1.107.0 in October 2026 is the defining recent case.

How do I check a setup.py before installing it?

Read the install-time code before it runs: look for custom install command classes, subprocess or os.system calls, base64 decoding, network requests, dynamic code evaluation, and any reference to .ssh, .aws or credential files. The scanner on this page flags each of those shapes line by line in your browser, with a plain-English explanation of each hit.

Why do swapped releases target install time?

Install time is the one moment code from a package executes automatically, with the installing user's permissions, files and environment — no import, no click, no vulnerability required. A credential stealer placed in an install hook runs on every laptop and CI runner that installs the package, which is why October 2026's swaps all carried install-time payloads.

Does a popular package protect me from a swap?

No — popularity is what the attacker is buying. LiteLLM's tampered 1.107.0 reached an ecosystem with about 23 million weekly downloads, per the October 2026 reporting, so one swapped release harvested at population scale. A famous name tells you the package was worth swapping; it says nothing about the artifact you are about to install.

What does the full tool check that this quick scan cannot?

This page pattern-matches the text you paste. The full release-swap-detector downloads the actual registry artifact, unpacks it, and diffs its contents against the maintainer's source repository at the same version, flagging code that exists in the release but not in the source — use it before concluding any suspect release was clean.
