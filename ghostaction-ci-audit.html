Your CI might already be leaking secrets — and the workflow looks helpful

In the GhostAction campaign, attackers compromised about 1,900 GitHub accounts and pushed malicious workflows into more than 30,000 repositories across 3,000 users and organizations — attempting to extract 3,174 secrets from CI in a single October 8–9, 2026 surge (per GitGuardian's research, reported October 15, 2026). The weapon is a workflow file with a reassuring name — security-audit.yml or github_actions_security.yml — pushed in your identity, which quietly sends your CI secrets to an attacker server. The original wave, first documented in September 2025, already exfiltrated at least 3,325 secrets from 817 repositories. How the attack works (per GitGuardian, The Hacker News, StepSecurity):
• Attacker steals a maintainer's credential — a leaked personal access token (PAT) from infostealer logs or credential dumps.
• Using the hijacked account, they push a workflow file named security-audit.yml (or github_actions_security.yml) straight to the default branch — bypassing pull-request review entirely.
• Every commit is made with the victim's own identity, so nothing looks out of place in the commit history.
• The attacker scraped existing workflow history for secret names already in use, then referenced those same names in the malicious workflow.
• When the workflow runs, it sends the secrets' values in a single curl POST to 193.32.204.199 — CI/CD secrets, cloud keys, npm/PyPI/DockerHub tokens, Anthropic, OpenAI and OpenRouter API keys.
• The October 2026 variant also swept the working tree and the entire git history for credentials — deleting the workflow after the fact doesn't un-leak anything.

⚠ What to do if you find something

  1. Rotate secrets FIRST, before you delete anything. Anything the workflow could read is already exfiltrated — deleting the file first just alerts the attacker while your secrets are still live.
  2. Remove the malicious workflow file from the default branch.
  3. Check your GitHub account for repositories, commits, or workflow runs you don't recognize — commits were made in victims' identities.
  4. Review the GitHub audit log for logins, token creations, and access grants you didn't make.
  5. Revoke and reissue every personal access token, then notify collaborators so they rotate their own credentials.
  6. If any secret was also valid for production systems (cloud keys, API keys), treat those systems as exposed and rotate there too.

Frequently asked questions

What is the GhostAction attack?

GhostAction is a GitHub supply-chain credential-theft campaign first documented by GitGuardian in September 2025. It escalated sharply on October 8–9, 2026: attackers compromised about 1,900 GitHub accounts and pushed malicious workflows into more than 30,000 repositories across 3,000 users and organizations, attempting to extract 3,174 secrets from public repositories' CI. The original 2025 wave hit 817 repositories across 327 users and exfiltrated at least 3,325 secrets.

How does GhostAction steal CI secrets?

Attackers gain write access using stolen personal access tokens (PATs) or credentials from infostealer logs and dumps. Using the hijacked maintainer's account, they push a malicious workflow file disguised with names like security-audit.yml or github_actions_security.yml directly to the default branch — bypassing pull-request review. The workflow reads the repository's configured Actions secrets (the attacker even scraped workflow history for secret names) and sends their values via a curl POST to the attacker-controlled IP 193.32.204.199.

How do I know if my repository was hit by GhostAction?

Look for: a security-audit.yml or github_actions_security.yml workflow you did not add; commits to workflow files you didn't author (commit messages seen include "Add security audit workflow" and "Update security audit workflow"); workflow runs you didn't trigger, especially workflow_dispatch runs; and any commits made in your identity that you don't recognize — every GhostAction commit was made with the victim's own identity.

What should I do if I find a malicious workflow in my repository?

Revoke and rotate ALL repository and organization secrets first — anything the workflow could read is already exfiltrated, so deleting the file alone changes nothing. Then remove the malicious workflow, check your GitHub account for rogue repos or commits, review the audit log for logins you don't recognize, revoke old personal access tokens, and notify collaborators so they can rotate their own credentials.

How do I harden GitHub Actions against supply-chain attacks?

Run the 7-step audit above: know every file in .github/workflows, review workflow-file commits and run history for anomalies, scope secrets so each workflow only reads what it needs, pin third-party actions to commit SHAs instead of floating tags, keep repository access least-privilege, and rotate personal access tokens regularly — stolen PATs were the attackers' way in.
