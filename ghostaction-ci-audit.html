Yes — immediately, before deleting the workflow. Any secret the workflow could read may already be copied: GitHub treats potentially exposed credentials as compromised. The October 2026 wave: how it escalated

Per GitGuardian's research, reported by The Hacker News on October 15, 2026 (thehackernews.com/2026/10/ghostaction-compromises-about-1900.html).

  • ~1,900 GitHub accounts compromised; 30,000+ repositories across 3,000 users/orgs targeted in the October 8–9, 2026 surge.
  • Payload evolution across three versions: v1 scanned git history for secrets (regexes for AWS keys, GitHub + GitLab tokens, AI secrets, cloud API keys); v2 added 2 lines of context around AWS key IDs; v3 added secret context retrieval.
  • GitHub began preventing the malicious workflow from running starting October 9, 2026 — later waves extracted nothing.
  • Attackers banked on UNROTATED secrets: victims of the September 2025 and August 2026 waves who never rotated were re-compromised.
  • Follow-up waves were observed October 10 and October 12, 2026 — no extraction, blocked.

October 2026 update: GhostAction's second stage — the fake font

Per OpenSourceMalware researcher Jenn Gile (reported by The Hacker News, GBHackers, October 16–19, 2026). Discovered by Thijs Xhaflaire (Jamf Threat Labs) while hunting PolinRider infections.

  • 94 compromised repos belonging to 66 owners carried the second stage (79 were cloned; the payload was confirmed in every accessible one; 15 were inaccessible). Most payloads appeared October 15, 2026 — and in 2 cases were added after owners had already removed the malicious workflows.
  • Three committed files: (1) .vscode/tasks.json with runOn: folderOpen — auto-runs when the folder opens in VS Code (task labeled "eslint-check", terminal visibility suppressed); (2) public/fonts/fa-solid-400.woff2 — not a font: 38 lines of unobfuscated Node.js credential stealer; (3) a second GitHub Actions workflow as a fallback if the stealer never runs (names seen: lint.yml, ci-check.yml, build-check.yml, repo-health.yml, audit.yml, code-review.yml, test-suite.yml — expanded credential formats plus a fallback upload to a secret gist).
  • Stealer targets: AWS keys, PyPI tokens, npm tokens, Git logins, Kubernetes credentials, SSH private keys (RSA + Ed25519, read in full), and Anthropic Claude + Google Gemini AI provider credentials; recursive credential-pattern hunt across the home directory; exfiltration via HTTP POST on port 8080 to 193.32.204.199.
  • Persistence that survives cleanup: a cron job every 5 minutes fetches an attacker script via a hostname-specific path and pipes it to bash (marker #ghc2). Deleting the repo files does NOT remove the cron foothold.
  • PolinRider copycat, not DPRK: the font filename matches North Korea's January 2026 PolinRider campaign, but researchers found no shared IOCs with DPRK malware — this is labeled a copycat.
  • Also new — GitHub-themed phishing: attackers registered my-github[.]com and sent fake GitHub security alerts harvesting credentials and 2FA codes; the infrastructure can also abuse GitHub OAuth to obtain repo and workflow tokens.
Honest scope: the stealer only runs if the VS Code workspace is trusted and automatic tasks are permitted — cloning or opening a repo alone does not execute it. Distinguish "the repo contains the files" from "the payload executed on a developer's machine." Remediation: revoke tokens and sessions, remove the cron persistence, and rotate exposed credentials from a clean device.
How the attack works (per GitGuardian, The Hacker News, StepSecurity):
• Attacker steals a maintainer's credential — a leaked personal access token (PAT) from infostealer logs or credential dumps.
• Using the hijacked account, they push a workflow file named security-audit.yml (or github_actions_security.yml) straight to the default branch — bypassing pull-request review entirely.
• Every commit is made with the victim's own identity, so nothing looks out of place in the commit history.
• The attacker scraped existing workflow history for secret names already in use, then referenced those same names in the malicious workflow.
• When the workflow runs, it sends the secrets' values in a single curl POST to 193.32.204.199 — CI/CD secrets, cloud keys, npm/PyPI/DockerHub tokens, Anthropic, OpenAI and OpenRouter API keys.
• The October 2026 variant also swept the working tree and the entire git history for credentials — deleting the workflow after the fact doesn't un-leak anything.

⚠ What to do if you find something

  1. Rotate secrets FIRST, before you delete anything. Anything the workflow could read is already exfiltrated — deleting the file first just alerts the attacker while your secrets are still live.
  2. Remove the malicious workflow file from the default branch.
  3. Check your GitHub account for repositories, commits, or workflow runs you don't recognize — commits were made in victims' identities.
  4. Review the GitHub audit log for logins, token creations, and access grants you didn't make.
  5. Revoke and reissue every personal access token, then notify collaborators so they rotate their own credentials.
  6. If any secret was also valid for production systems (cloud keys, API keys), treat those systems as exposed and rotate there too.

Frequently asked questions

What is the GhostAction attack?

GhostAction is a GitHub supply-chain credential-theft campaign first documented by GitGuardian in September 2025. It escalated sharply on October 8–9, 2026: attackers compromised about 1,900 GitHub accounts and pushed malicious workflows into more than 30,000 repositories across 3,000 users and organizations, attempting to extract 3,174 secrets from public repositories' CI. The original 2025 wave hit 817 repositories across 327 users and exfiltrated at least 3,325 secrets.

What are the GhostAction malicious workflow file names?

Three distinct workflow file names have been confirmed across the GhostAction waves: security-audit.yml (the 2026 variant, which also mines full git history), github_actions_security.yml (display name 'Github Actions Security'), and security-check.yml (display name 'Security Check'). All three trigger on push events and exfiltrate secrets via curl to attacker infrastructure. (Per Decryption Digest and StepSecurity, Oct 2026.)

How do I know if my repository was hit by GhostAction?

Look for: a security-audit.yml or github_actions_security.yml workflow you did not add; commits to workflow files you didn't author (commit messages seen include 'Add security audit workflow' and 'Update security audit workflow'); workflow runs you didn't trigger, especially workflow_dispatch runs; and any commits made in your identity that you don't recognize — every GhostAction commit was made with the victim's own identity.

Why isn't deleting the workflow enough?

If the malicious workflow executed successfully, any secret available to it may already have been copied by the attacker. GitHub's incident-response guidance recommends treating potentially exposed credentials as compromised: revoke or rotate the affected credentials first, then remove the workflow from all branches. Cleanup alone does not end the threat. (Per CyberUpdates365 and GitHub guidance.)

How do I harden GitHub Actions against supply-chain attacks?

The 7-step audit above covers the essentials: know every file in .github/workflows, review workflow-file commits and run history for anomalies, scope secrets so each workflow only reads what it needs, pin third-party actions to commit SHAs instead of floating tags, keep repository access least-privilege, and rotate personal access tokens regularly — stolen PATs were the attackers' way in.

How does the GhostAction fake-font stealer work?

The second stage commits three files: .vscode/tasks.json (a VS Code task labeled "eslint-check" with runOn: folderOpen and a hidden terminal), public/fonts/fa-solid-400.woff2 (38 lines of unobfuscated Node.js — not a font), and a fallback GitHub Actions workflow. When the folder opens in a trusted VS Code workspace with automatic tasks allowed, the stealer runs: it harvests AWS keys, PyPI/npm tokens, Git logins, Kubernetes credentials, SSH private keys (RSA + Ed25519 in full), and Anthropic Claude / Google Gemini credentials via a recursive home-directory hunt, exfiltrating over HTTP port 8080 to 193.32.204.199. It also installs a cron job (marker #ghc2) fetching and running attacker code every 5 minutes — so deleting the repo files does not remove the foothold. OpenSourceMalware found it in 94 repos across 66 owners (October 2026). (Per OpenSourceMalware, The Hacker News, GBHackers.)
