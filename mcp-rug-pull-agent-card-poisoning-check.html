MCP RUG PULLS & AGENT CARD POISONING — SUPPLY-CHAIN EXPLOIT — OCT 2026

You approved the tool on day 1. On day 30 it rewrote its own instructions.

An MCP rug pull is a supply-chain exploit where an external tool server or peer agent mutates its metadata schemas after your initial approval to inject hidden instructions — and MCP has no built-in mechanism to detect the change. Pair it with Agent Card poisoning — unsigned Agent-to-Agent agent.json manifests tampered with after approval — and attackers get remote code execution and silent credential exfiltration across your agent fleet. This is not theoretical: the Deadbugz campaign (August 2026) weaponized exactly this lifecycle. Eight questions, sixty seconds: is your agent supply chain exposed? Free, no signup.

The short answer: An MCP rug pull shows you clean tools, earns your approval, then changes the tool definitions afterward — no re-approval, no notification. Agent Card poisoning does the same to unsigned agent.json manifests your agents ingest to discover peers. Defend with cryptographic pinning: hash each server’s full tool record at approval, re-approve on any change, require signed agent cards, and diff approved snapshots against live metadata in CI.
What: MCP rug pulls = post-approval metadata mutation by external tool servers or peer agents; Agent Card poisoning = tampered unsigned A2A agent.json manifests. Combined impact: RCE + silent credential exfiltration.
CVEs: CVE-2025-6514 (mcp-remote STDIO command injection) and CVE-2025-6515 (session ID hijacking) showed trusting dynamic protocol metadata is not safe.
Real case: Deadbugz (Pillar Security / CSA, Aug 2026) — a malicious MCP server distributed via public GitHub PRs disguised as a benign text-formatting tool. It withheld its payload until the agent made three ordinary tool calls, then silently rewrote its own tool metadata to hunt SSH keys, AWS credentials, shell history, and Kubernetes configs. 23 PRs pushed in a 74-minute window on Aug 10, 2026.
Fixes: hash the canonical whole tool record (top-level description, full inputSchema including nested property descriptions, annotations) plus launch command and args; re-approve on any change; file-integrity monitoring on mcp.json; pin exact versions (no unpinned npx/uvx).
Sources: “MCP Rug Pulls & Agent Card Poisoning: The Exploit Breaking A2A Protocols” (Asif Muhammad Iqbal, Logic42, Oct 2026); CSA research note on Deadbugz (Aug 2026); MCP security testing guidance (dev.to, Oct 2026).

The 8-question agent-supply-chain check

A “Yes” means the defense is in place; a “No” is a supply-chain gap.

1. Do you pin a hash of each MCP server’s full tool record (description, full inputSchema including nested property descriptions, annotations) at approval time?

2. Does your client re-prompt for approval or block when a connected server’s tool metadata changes?

3. Are unsigned agent.json manifests rejected or quarantined before any agent acts on them?

4. Do you verify signatures on Agent Cards and re-verify on every re-fetch, not just at first connect?

5. Is mcp.json and other MCP server-config files under file-integrity monitoring or version-control review?

6. Are MCP server versions pinned to exact versions (no unpinned npx/uvx latest)?

7. Do you diff approved tool snapshots against live server metadata in CI?

8. Are agent-to-agent delegation paths restricted to a vetted allowlist of peer agents?

Why the rug pull beats install-time security

  • Approval is a snapshot; the server is a live feed. Your client shows you the tools once and re-reads them on every reconnect — without re-prompting. The trust you granted day 1 silently transfers to day 30’s mutated tools.
  • Runtime-gating defeats static review. Deadbugz behaved benignly through its first three tool calls and only then weaponized — install-time and static review see nothing.
  • Descriptions are payloads. The model reads the full tool description and input schema; your UI shows a tidy label. The gap between what the model reads and what you see is the vulnerability.
  • Unsigned agent cards are unsigned trust. In A2A swarms, agents ingest agent.json manifests to discover peers. Unsigned means anyone in the path can rewrite who your agent delegates to.
  • Never calling a poisoned tool does not save you. Most hosts load connected servers’ tool descriptions into the model’s context on connect — connecting is the trust decision.

What this checker does NOT do

  • It does not scan your MCP servers, configs, or agent cards for tampering.
  • It cannot detect whether a rug pull or card poisoning has already happened — that needs metadata drift forensics.
  • It is informational, not a security audit. Treat any unpinned, unhashed server as potentially mutated until verified.

Frequently asked questions

What is an MCP rug pull?

An MCP rug pull is a supply-chain exploit where an external MCP tool server (or peer agent) mutates its metadata schemas — tool descriptions, input schemas — after you approved it, injecting hidden instructions the agent will follow. Day 1 the tools look safe; day 30 an update rewrites a tool description to exfiltrate credentials. MCP has no built-in mechanism to detect that a tool’s definition changed after you consented to it, so the malicious version inherits the trust you granted the original.

What is Agent Card poisoning?

Agent Card poisoning targets Agent-to-Agent (A2A) protocols: autonomous agents discover and delegate to peer agents by ingesting their Agent Cards — agent.json manifests. When those manifests are unsigned, an attacker can tamper with them after approval, redirecting delegation or injecting instructions. The result can be remote code execution and silent credential exfiltration across the agent swarm.

Has an MCP rug pull happened in the real world?

Yes. In August 2026, Pillar Security researchers identified “Deadbugz,” an active campaign distributing a malicious MCP server via public GitHub pull requests disguised as a benign text-formatting tool. The server withheld its payload until the connected agent had made three ordinary tool calls, then silently rewrote its own tool metadata to hunt SSH keys, AWS credentials, shell history, and Kubernetes configs — the runtime-gated rug-pull lifecycle. It pushed 23 pull requests to unrelated repositories within a 74-minute window on August 10, 2026.

How do I protect against MCP rug pulls?

Pin a cryptographic hash of each server’s full tool record — description, inputSchema including nested property descriptions, and annotations — plus the launch command and args, at approval time. Re-approve (or block) on any change. Diff approved tool snapshots in CI against live server metadata. Pin exact server versions (no unpinned npx/uvx). Put mcp.json under file-integrity monitoring. The 8-question checker on this page grades your setup.

How do I protect against Agent Card poisoning?

Reject or quarantine unsigned agent.json manifests before any agent acts on them. Verify signatures on Agent Cards and re-verify on every re-fetch, not just at first connect — a card approved clean can be tampered with later. Restrict agent-to-agent delegation to a vetted allowlist of peer agents so a poisoned card cannot redirect work to an attacker’s agent.
